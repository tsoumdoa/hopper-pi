Pull request review

Good boundary. Weak readiness and ordering.

The PR makes Rhino own a private Node host and removes the need for a Grasshopper component. That is a sensible direction. It is not yet a dependable runtime: "host ready" does not mean Grasshopper is ready, mutation completion is not observed, and the two paths into Rhino's main thread are not ordered together.

Recommendation Do not merge as production-ready. Merge behind an experimental flag, or fix readiness, completion semantics, and main-thread scheduling first.

Short answer

What the PR actually does

Rhino owns the session

Hopper.Rhino.rhp starts the ZMQ bridge, launches one child Node process, opens the browser, and stops both when Rhino closes.

Node is private, but large

The Yak carries an embedded Pi runtime, provider SDKs, web UI, native ZeroMQ modules, and two full Node executables.

Ready means too little

The ready line proves only that the Node HTTP server started. It says nothing about Grasshopper, an active GH document, or ZMQ command capability.

Async transport, incomplete protocol

Mutations are queued, but the caller receives success after send, not after execution. Queries can overtake queued changes.

What is solid. Loopback binding, per-launch browser tokens, origin checks, PID validation, instance-specific connection profiles, pinned Pi versions, checked Node downloads, and parent-process monitoring are all good decisions. The process boundary also protects Rhino from most Node and model-runtime work.

Confirmed bloat

  • Two Node binaries per package. Only one runs after installation. Publishing architecture-specific artifacts would save about 108 to 110 MB unpacked.
  • All ZeroMQ native builds. The macOS package contains Linux, Windows, x64, arm64, and ia32 add-ons. The zeromq package is about 20 MB; roughly 15 MB is for non-macOS targets.
  • Development output in the runtime. The build copies all of dist. It contains 146 source maps and 52 compiled test files or test maps. It also retains dist/services/rhino-visual-consent.js even though the source file no longer exists, because the build never cleans dist.
  • Unreachable application modules. A conservative import walk found 38 compiled JavaScript files not reachable from dist/host/index.js. Static web assets are included in that number and are valid, but tests, the dump script, stale output, and the unused subscriber are not.
  • Runtime-irrelevant files. The staged host includes the pnpm lockfile, workspace file, and the Grasshopper installer script. package.json is useful for ESM and dependency resolution; the others are not needed to run.
  • Unused direct dependency. Hopper imports no chalk source directly. Removing it as a direct dependency will not remove the package because Pi also depends on it, but the manifest should still tell the truth.

Suggested package target. First split packages by OS and CPU, clean dist, exclude tests and maps, and prune native add-ons to the target. Those changes are low risk. Bundling or trimming the Pi dependency tree comes later because dynamic imports and native modules make aggressive tree-shaking easy to get wrong.

Question 2

Who owns each server?

There are two servers and one client host. The names make this harder to see than it should be.

_HopperRhino command on UI thread

Node process lifecycle

HopperHostManager starts one child for each backend instance. It waits up to 60 seconds for a validated JSON ready line, probes /health every 5 seconds, and opens the browser.

Node-side servers

One Node process owns the HTTP static server and WebSocket server. It accepts one authenticated controller tab. A new tab replaces the old one.

ZMQ server lifecycle

HopperBackendRuntime.Shared owns PUB, PULL, and REP sockets inside Rhino. The new RHP and the legacy GHA share this singleton.

Startup

  1. _Hopper calls StartBackend() synchronously on Rhino's UI thread.
  2. The backend binds ZMQ endpoints, writes an instance profile, starts three worker tasks, subscribes to Rhino closing, and begins tracking the active GH document.
  3. The RHP launches the bundled Node executable with the exact connection-profile path and Rhino PID.
  4. Node creates the Pi session, starts HTTP and WebSocket servers, then prints a tokenized URL to stdout.
  5. A .NET process-output callback validates the PID and URL, starts health polling, and opens the browser.

Shutdown

  1. Rhino's closing event disposes the host manager, then stops the backend. The backend also has its own closing subscription, so stopping is idempotent but duplicated.
  2. The host manager performs a synchronous authenticated HTTP shutdown call, waits up to 6 seconds, kills the process tree if needed, then waits again.
  3. Node first closes browser connections and the HTTP server, then disposes the Pi runtime. A 5-second force-exit timer is the last guard.
  4. The Node child also polls its parent PID every 2 seconds, so it shuts itself down if Rhino vanishes without a clean closing event.

Main-thread shutdown can stall Rhino. HopperRhinoPlugin.OnRhinoClosing runs in Rhino, while HopperHostManager.Dispose() performs synchronous HTTP and process waits. ZMQ and job disposal then use more synchronous waits. The configured bounds can add up to roughly 16 seconds in the worst path. Closing should signal cancellation immediately and move waits off the UI thread, with a short final kill fallback.

No automatic recovery. A failed health check only sets Healthy = false. It does not change the host state, restart the child, or use retry backoff. An unexpected process exit requires the user to run _Hopper again.

Persistent state has no retention policy. The runtime keys session and workspace folders by Rhino PID plus a fresh backend GUID. This isolates concurrent Rhino processes, but a Rhino restart does not continue the prior session and old instance folders remain on disk. Crashes can also leave instance connection profiles behind. Add an explicit continuity policy and clean stale instance data by age and verified-dead PID.

Lifecycle references: HopperHostManager.cs:75–304, 462–518, src/host/index.ts:15–57, src/host/lifecycle.ts:15–29.

Thread model

No, it does not all run on main

The process and thread split is mostly appropriate. Rhino and Grasshopper object access must stay on Rhino's main thread. Networking, model calls, browser traffic, health checks, and waiting should not.

Execution contextCurrent workAssessment
Rhino UI thread _Hopper, backend startup, initial socket creation and bind, all Rhino/GH operations, canvas serialization, some shutdown waits Object operations belong here. Network construction, long batches, and process waits do not.
.NET worker task 1 PULL command receive loop and PUB queue draining Correct idea. Socket ownership should be explicit and single-threaded.
.NET worker task 2 REP synchronous request loop Correct idea, but it independently posts work to main, so it races the job path.
.NET worker task 3 Waits for jobs, drains the entire queue, posts one batch to the UI thread, then blocks for completion The worker may block. The unbounded single UI batch is the problem.
.NET thread pool callbacks Process stdout/stderr/exit, readiness timeout, health timer and HTTP continuation Fine. State locking is present.
Node process event loop HTTP, WebSocket dispatch, Pi session coordination, async ZMQ clients Separate from Rhino and non-blocking for normal I/O. CPU-heavy JavaScript would still block this event loop.
Browser process UI rendering and user input Fully isolated from Rhino.

NetMQ thread ownership is risky. The sockets are constructed and bound on the Rhino UI thread, used by worker tasks, and disposed again from the shutdown thread while receive loops may still be active. NetMQ sockets should have one owner thread. A NetMQPoller plus NetMQQueue, or a dedicated transport thread that creates, binds, polls, and disposes every socket, would remove this ambiguity.

Question 3

Grasshopper is not guaranteed to be running

The concern is correct. _Hopper starts the bridge and Node host without loading Grasshopper or waiting for a canvas document. A backend ping succeeds because ping never touches the GH document. The browser can therefore show "Ready" while every gh_* tool is about to fail.

Current meaning of ready

  • Node created a Pi session.
  • HTTP and WebSocket servers bound a loopback port.
  • The stdout ready message had the expected PID and a valid tokenized URL.

It does not prove ZMQ health, Grasshopper load state, an active canvas, or an active document.

What ready should mean

  • Rhino bridge accepts authenticated requests.
  • Grasshopper's plug-in and component server are loaded.
  • An active GH document exists for GH-scoped work.
  • The dispatcher can accept a bounded work item.

Rhino-only tools may become ready earlier. Report capabilities separately.

host_starting→ bridge_ready→ grasshopper_loading→ awaiting_document→ gh_ready

Better startup contract

  1. Run _Hopper on Rhino's command thread as today.
  2. On that thread, ask Rhino to load the Grasshopper plug-in through its plug-in API or the supported Grasshopper command. Do this once. Do not poll blindly from Node.
  3. Have the bridge expose a typed getRuntimeStatus request with separate fields for Rhino, ZMQ, Grasshopper, active document, queue depth, and shutting down state.
  4. If Grasshopper is loaded but has no document, keep the host alive and mark only GH tools unavailable. Ask the user to open or create a document. Do not silently create one unless that product behavior is explicit.
  5. Signal readiness changes from GH document or canvas lifecycle events. Use a slow idle fallback only where Rhino/Grasshopper offers no reliable event.
  6. Disable or guard gh_* tools until gh_ready. Keep rh_* tools available when the Rhino document is valid.

Do not make startup wait forever for a document. Loading Grasshopper is a startup responsibility. Choosing or creating a GH document is user state. Model those as separate conditions, show them in the browser, and let queued GH work expire with a clear NO_ACTIVE_GRASSHOPPER_DOCUMENT result.

Readiness references: HopperCommands.cs:13–33, RhinoZmqPlugin.cs:123–165, 223–251, ActiveGrasshopperDocumentTracker.cs:23–45.

Execution design

There is a queue, but it is not the queue you need

The current JobQueue does marshal mutations to Rhino's main thread. That answers only thread affinity. It does not provide completion, ordering across request types, backpressure, or safe timeout behavior.

Concrete failure mode

  1. The agent sends gh_edit_components.
  2. submitCommand() resolves after ZeroMQ accepts the message. It returns a job ID to the agent.
  3. The agent immediately calls getCurrentCanvas over the independent REP socket.
  4. The REP worker may reach the UI thread before the queued mutation batch.
  5. The agent sees the old canvas and may duplicate or contradict its own edit.

The code already contains a Subscriber and job-status types, but nothing imports the subscriber. The bridge publishes queued, running, completed, and failed events that the embedded host never consumes.

Recommended queue model

Async requestID + capability + deadline
Transport ownervalidates and admits
Bounded channelone ordered stream
UI pumpone item or time budget
ExecuteRhino/GH only here
Complete TCSresult or explicit unknown
Awaited resultagent continues in order
  • One ordered dispatcher. Send mutations and document-sensitive queries through the same main-thread work queue. Health pings and static status reads can bypass it.
  • Bound the queue. Reject excess work with BUSY and include queue depth. An unbounded agent-driven queue is a memory and responsiveness risk.
  • Dispatch in small units. Execute one item per UI callback, or stop after a short time budget and repost. Never drain an arbitrary batch in one UI turn.
  • Await real completion. The Node caller should resolve when the main-thread item completes, not when PUSH sends. A correlation ID plus a completion response is enough.
  • Define cancellation states. A cancelled item that has not started must never run later. Once execution begins, return OUTCOME_UNKNOWN on timeout unless the operation proves rollback.
  • Gate by capability. Rhino-only work needs a Rhino document. GH work also needs Grasshopper and an active GH document. A waiting item gets a deadline, not infinite patience.

The desired model is achievable. Node and ZMQ remain asynchronous and off the UI thread. Each request awaits a task or promise without blocking those event loops. Only the small delegate that touches Rhino or Grasshopper runs on main.

Question 4

The codebase is in a transitional shape

The new responsibilities are real, but the folders still describe the old proof of concept. The result works against maintenance: a project inside Hopper.Backend/ compiles parent-folder globs, the namespace is still rhino_zmq_poc, and host code is mixed into the old extension source tree.

High Host readiness ignores Grasshopper and the active document. The browser reports ready while GH tools predictably fail. Add capability-aware status and load Grasshopper during _Hopper.
High Mutation calls resolve after send, not execution. Queries can overtake edits; failures arrive after the agent has moved on. Await correlated completion through a unified dispatcher.

Medium Tests do not cover the critical Rhino lifecycle. The new host-manager tests validate parsing and paths, not process start, health transition, restart, UI-thread dispatch, or GH readiness. Add component tests with fakes and at least one Rhino integration smoke test.

Recommended changes

A practical order of work

1. Fix before calling it ready

  1. Add runtime capability status.
  2. Load Grasshopper from _Hopper.
  3. Unify main-thread dispatch.
  4. Await mutation completion.
  5. Move shutdown waits off main.

2. Fix before distributing

  1. Clean and allowlist release output.
  2. Split CPU packages.
  3. Prune native ZeroMQ targets.
  4. Add a Yak size regression check.
  5. Smoke-test both CPU artifacts in CI.

3. Pay down structure

  1. Move shared C# sources under their project.
  2. Separate host, extension, protocol, and web code.
  3. Remove dead modules and stale names.
  4. Generate or contract-test both sides of the wire protocol.

Acceptance criteria

Readiness
_Hopper either loads Grasshopper or reports a typed failure. The browser distinguishes Rhino ready, bridge ready, GH loaded, and active document. GH tools cannot run before their capability is ready.
Ordering and completion
A mutation followed by a query always returns a query result that includes the mutation. The mutation promise resolves only after execution. Queue-full, cancelled-before-start, timed-out-while-running, and rollback results are distinct.
Responsiveness
Networking and waiting never block Rhino's UI thread. A queue burst cannot run as one unbounded UI batch. Closing Rhino does not wait on synchronous HTTP or multi-second task joins.
Lifecycle
Unexpected Node exit transitions status and can restart with a bounded backoff. Rhino exit kills the process tree if graceful shutdown misses its deadline. Starting _Hopper twice remains idempotent.
Packaging
The release staging directory starts empty. It contains no test files, source maps, stale compiled modules, lockfile, workspace file, installer script, wrong-OS native add-ons, or wrong-CPU Node binary. CI enforces the allowlist and size budget.
