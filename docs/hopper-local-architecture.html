Architecture plan, revision 1

Trimmed architecture

Pi inside Hopper, without putting Pi inside Rhino.

Rhino launches one private Hopper host. That host serves the browser UI, embeds Pi through its SDK, and uses the existing ZMQ bridge to edit Rhino and Grasshopper.

The main decision

No Pi CLI child process and no Pi RPC adapter. The web server and Pi runtime share one Node process.

Keep

  • ✓
    Local web UI

    The browser remains separate from Rhino and can reconnect after a refresh.

  • ✓
    Private Pi installation

    Hopper pins its SDK and uses private settings, stored credentials, skills, and sessions. Provider keys inherited from the environment remain available.

  • ✓
    Existing ZMQ bridge

    The current Rhino and Grasshopper command path stays in place.

  • ✓
    One host per Rhino instance

    No routing layer or instance picker is needed.

Remove or defer

  • ×
    Pi CLI subprocess

    The Hopper host creates the Pi session in its own process through the SDK.

  • ×
    Pi JSONL RPC

    There is no second process that needs an RPC translator or health monitor.

  • ×
    Required GHZMQ component

    The plug-in owns the backend. The component can remain as an optional status view.

  • →
    Replacing ZMQ

    Deferred. A new transport would add work without helping the first release.

Implementation plan

  1. Prove the embedded agent

    Create a local Hopper host that starts a Pi session runtime, loads only the bundled extensions and skills, binds browser-backed extension UI, and reaches the current ZMQ backend.

  2. Add the browser conversation

    Serve one chat page with streaming text, visible tool calls, stop, new session, and the existing ask-user interactions.

  3. Give Rhino ownership

    Add the _Hopper command, host health checks, browser launch, active-document tracking, and clean shutdown.

  4. Remove the canvas dependency

    Move backend ownership out of the GHZMQ component. Keep that component only if its canvas status output remains useful.

  5. Package both platforms

    Bundle pinned Node 22.22.3 x64 and arm64 runtimes, exact Pi and Hopper versions, and native ZMQ builds in separate Windows and macOS Rhino packages.

Decision summary: browser UI stays, Pi RPC goes. Browser → Hopper host → ZMQ → Rhino/GH
