Port Hopper from a Pi extension to an MCP server

Keep the working Rhino and Grasshopper bridge. Replace the Pi-only agent boundary with a small, standards-based MCP server that any compatible host can launch.

Brief

Explore what it looks like to port this project to an MCP-based project following the 2026-07-28 specification.

Recommended shape

Make the TypeScript process the MCP server and keep ZeroMQ as its private bridge to the Grasshopper plugin. Ship stdio first with the stable @modelcontextprotocol/server v2 SDK. Keep the Pi adapter for one release while both adapters call the same framework-neutral handlers.

This is a boundary refactor, not a C# rewrite. Most of the parser, command, validation, and Grasshopper code remains useful as-is.

02

Decisions to make up front

Adopt

stdio as the first transport

Hopper is a local companion to Rhino. A host launches the server, credentials stay in the environment, and the MCP endpoint never becomes a network service. Use serveStdio(factory).

Adopt

One deterministic tool list

Register the 15 catalog tools plus rh_capture_view in stable name order. Remove session-specific activation. This matches the 2026 rule that list results no longer vary by connection.

Defer

Streamable HTTP

Add it only for a real remote or multi-host use case. It needs Origin checks, localhost binding by default, MCP request headers, and the authorization framework. There is no payoff for the first local release.

Defer

Tasks extension

The current bridge can preserve queued jobId results without adopting Tasks. Add durable task handles later if long Rhino jobs need polling, reconnection, or mid-flight input.

Compatibility posture: write handlers for the 2026 model, then let the v2 SDK serve modern and legacy clients from the same stdio entry during rollout. Add a --modern-only switch instead of hard-cutting older hosts on day one.

Subscriptions

Start after read and mutation tools are stable. Request-scoped progress remains on the tool call response, not the subscription stream.

Tasks
Optional later extension

Candidate for queued commands and long script runs.

Do not make the first MCP release depend on extension support. Preserve explicit jobId fields now, which leaves a clean migration path.

Remove from the MCP catalog

  • ask_userIt is a Pi host UI wrapper. MCP clients own user interaction. Server-initiated questions use MRTR elicitation inside the operation that needs input.
  • pick_optionSame reason. Convert only real server-side choices to elicitation schemas.
  • hopper_search_toolsIt mutates a session-scoped active tool set. Replace it with deterministic tools/list, compact descriptions, and host-side selection.

Add to every tool definition

  • titleUse the current Pi label.
  • annotationsSet read-only, destructive, idempotent, and open-world hints conservatively. Treat them as display hints, never authorization.
  • outputDefine a stable machine result. Keep the compact human text because older clients and models still benefit from it.
  • errorsReturn isError: true for offline backend, validation, and Rhino execution failures.
04

Fix the lifecycle mismatches

Transactions become per call

Pi currently begins Grasshopper and Rhino transactions at agent_start and commits them at agent_end. MCP has no model-turn lifecycle. Wrap each mutating tool handler in begin, commit, and cancel. Keep gh_apply_graph as the preferred multi-edit atomic operation.

Acceptance

A failed mutation leaves no partial edit and one successful tool call creates one undo step.

State uses explicit handles

Do not infer identity or state from a protocol session. Current ZMQ connection discovery may remain process-local. Any future cross-call transaction or durable job must return a server-minted handle and accept it as an ordinary argument.

Acceptance

Restarting the MCP process does not leave an invisible open transaction in Rhino.

Consent moves into the call

before_agent_start can no longer inspect the prompt or switch models. Always advertise rh_capture_view. If the host lacks image support it may ignore the tool. When consent is unknown, return an elicitation request or a clear tool error if the client cannot elicit.

Acceptance

No pixels leave Rhino until the call has an explicit approval or the documented environment override.

Cancellation reaches the bridge

Thread the MCP request signal through tool handlers and ZeroMQ waits. For synchronous calls, stop waiting and close the request cleanly. For queued edits, add a best-effort cancel command only where the C# job queue can safely honor it.

Acceptance

Canceling a stdio request produces no later response or progress notification for that request.

06

The key interfaces

The useful seam is small. Each tool owns portable metadata and a handler. Pi and MCP adapters translate at the edge.

src/core/tool-contract.ts 
export interface HopperToolSpec<Input, Output> {
  name: string;
  title: string;
  description: string;
  inputSchema: JsonSchema2020;
  outputSchema: JsonSchema2020;
  annotations: {
    readOnlyHint: boolean;
    destructiveHint: boolean;
    idempotentHint: boolean;
    openWorldHint: boolean;
  };
  execute(input: Input, ctx: HopperCallContext): Promise<HopperResult<Output>>;
}
src/mcp/create-server.ts 
const server = new McpServer(
  { name: "hopper-mcp", version: packageVersion },
  { instructions: hopperInstructions }
);

for (const tool of hopperTools) {
  server.registerTool(tool.name, {
    title: tool.title,
    description: tool.description,
    inputSchema: fromJsonSchema(tool.inputSchema),
    outputSchema: fromJsonSchema(tool.outputSchema),
    annotations: tool.annotations
  }, async (input, ctx) => toMcpResult(
    await tool.execute(input, fromMcpContext(ctx))
  ));
}
Why keep raw JSON Schema for the first port?
The project already emits TypeBox-style JSON schemas, including a deliberate 2020-12 tuple for gh_apply_graph. The v2 SDK supports fromJsonSchema() and performs runtime validation. Rewriting every tool in Zod at the same time would mix a protocol migration with a schema rewrite and make parity harder to prove.
What happens to the current Pi entry?
Move it to src/pi/index.ts. Its lifecycle and TUI features remain available during the bridge release, but its tools adapt the shared registry. Once MCP hosts cover viewport consent, model capability filtering, and normal install flows, remove the Pi entry and the three @earendil-works dependencies.

08

Risks and mitigations

Loss of one-undo-step-per-agent-turn
High
Document the semantic change, use per-call transactions, and steer new builds through atomic gh_apply_graph. Do not fake a turn boundary MCP cannot observe.
Schema drift during adapter work
High
Freeze current schemas first and use fromJsonSchema(). Add 2020-12 validation and a golden tools/list fixture before changing descriptions.
Viewport data leaves Rhino without consent
High
Require MRTR elicitation or the explicit environment override. Treat tool annotations as untrusted display hints, not permission.
A canceled MCP call keeps editing Rhino
High
Propagate cancellation through the TypeScript wait path. Add C# queue cancellation only where operations can stop safely. Report the limit for already-running Rhino UI work.
Host compatibility varies
Medium
Serve both protocol eras during rollout, test with Inspector and two real hosts, and keep optional features out of the first release.
Remote transport expands the attack area
Medium
Do not ship HTTP first. If added, use the SDK handler, Origin validation, localhost defaults, and the MCP authorization spec. Never expose raw ZMQ ports.
09

Open product choices

Keep one npm package or publish a new server package?

My default is one package with two executable entries during the bridge release. Split only if Pi and MCP need different release cadences.

Decide with: maintainer and release owner

How much legacy client support is worth carrying?

The SDK can serve both eras. Set a removal condition now, such as two named hosts supporting 2026-07-28, so compatibility code does not become permanent by accident.

Decide with: supported-host list

Should queued edits become MCP Tasks?

Answer after measuring real tool durations and host extension support. A job that returns in a few seconds does not need a durable task. A job that must survive reconnects does.

Decide with: usage data after the core port

Should reference material become prompts, resources, or a future Skills extension?

Use prompts and resources now because they are stable server primitives. Keep the content modular so it can move to Skills over MCP if the extension and target hosts settle on an interoperable shape.

Decide with: client support matrix

Specification basis

Protocol

MCP 2026-07-28 specification and key changes. These define stateless requests, per-request capabilities, server/discover, MRTR, subscriptions, caching fields, and removed session behavior.

Transport

stdio transport and Streamable HTTP. These support the stdio-first decision and the HTTP security requirements.

Server features

Tools, resources, prompts, and discovery.

Implementation

Official TypeScript SDK v2, its protocol-era guide, and raw JSON Schema support.

Optional extension

MCP Tasks. It is useful for durable long-running work but is deliberately outside the first port.
