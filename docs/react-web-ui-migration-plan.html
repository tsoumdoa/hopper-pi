Hopper React web UI migration

00 / boundary

The client changes. The private system does not.

The browser continues to connect only to the local Hopper host over WebSocket and authenticated HTTP. The host remains the single gateway to the embedded Pi runtime, Rhino RPC, and Grasshopper operations.

Non-negotiable production rule

The packaged app binds to loopback, keeps its token authentication and origin checks, and never exposes ZeroMQ or Rhino directly to the browser.

KeepToken handoff, session snapshots, reconnect behavior, runtime polling, provider flows, and agent-owned dialogs.
ReplaceThe static HTML, direct DOM mutation, hand-written responsive CSS, and one large mutable browser-state object.
Do not addA public API server, browser-to-Rhino path, or a second source of truth for the agent session.
01 / state

Use a reducer first.

Hopper has one controller, one WebSocket event stream, and a server-owned session. React useReducer fits that shape cleanly. It keeps every incoming event as an explicit state transition without introducing an extra client-state framework.

Decision

Use useReducer, context, and two hooks: one for the WebSocket connection and one for authenticated runtime-status polling. Do not add Zustand, Redux, Jotai, or TanStack Query during the migration.

Reducer ownsConnection display state, session snapshot, messages, streaming assistant output, tool calls, pending dialogs, models, providers, notices, and latest runtime status.
Hooks ownSocket lifecycle, timers, HTTP fetches, session storage, cleanup, and command functions.
Components ownRendering state and invoking typed commands. They do not interpret raw WebSocket payloads.

03 / UI system

Editorial control room, built from owned primitives.

The app keeps Hopper's warm paper, forest green, and orange working states, but gains cleaner type hierarchy, more deliberate spacing, and a clearer distinction between live work and configuration. shadcn/ui supplies accessible base components that remain editable inside the repository.

04 / delivery

Build in layers, validate behavior at each boundary.

01

Protect the existing contract

Extract browser-safe protocol types, record representative events as fixtures, and strengthen host authentication tests.

02

Install the client foundation

Add React, Vite, Tailwind, shadcn/ui, a web TypeScript configuration, and a production output path of dist/host/static.

03

Implement state and transport

Create the reducer, context, normalizers, WebSocket hook, and runtime-status hook before building feature components.

04

Port the product behavior

Move sidebar, runtime status, history, streamed messages, tools, composer, provider flow, queued dialogs, and toast handling in that order.

05

Enable safe local development

Allow one explicitly configured Vite development origin and proxy its requests. Production remains strict same-origin and loopback-only.

06

Package and retire the old UI

Test Vite asset serving and the Rhino package, then delete the legacy static files only after the release build passes.

05 / exit gates

Completion means a safe packaged client, not a pretty local page.

Release gate

A Vite development server is never required for a Rhino-launched session. The final Yak package must contain the built UI assets and retain the host's security controls.

  • Launch from Rhino, authenticate, restore a snapshot, send a prompt, and render streamed tool status.
  • Verify login, logout, model selection, thinking selection, abort, new session, and agent dialogs.
  • Verify mobile keyboard access, focus order, and reduced-motion behavior.
  • Pass Node type checks, frontend type checks, unit tests, browser smoke coverage, release build, and Rhino package verification.
